# Структура бэкенда

Бэкенд остаётся одним Django-сервисом с общей базой. Код разделён по назначению:

| Приложение | Назначение |
| --- | --- |
| `accounts` | Пользователи, вход, JWT, роли, модерация и профили |
| `training` | Учебные разделы, периоды, таблицы и расписания |
| `journals` | Журналы боевой подготовки и их предметы |
| `submissions` | Отправка и пересылка документов, история, прочтение, согласование исправлений |
| `methodical` | Методические материалы, предметы, башкармалыктар, просмотр DOCX |
| `news` | Новости, вложения, отметки прочтения и реакции |
| `plans` | Планы боевой подготовки и отметки прочтения |
| `content` | Баннеры и шаблоны разделов |
| `messaging` | Чат, рассылки и непрочитанные сообщения |
| `dashboard` | Личные кабинеты, сводки и рейтинги |

`common` содержит общий редактор JSON для админки и проверки совместимости.
В приложениях находятся собственные модели, обработчики, маршруты,
сериализаторы, административные классы и тесты. Общие для приложения операции
вынесены в `services.py`, настройки разделов — в `constants.py`.

## Совместимость с существующей базой

Для существующих моделей сохранён `Meta.app_label = "accounts"`.
Это сохранение идентификатора модели в Django, хотя её реализация теперь
находится в соответствующем приложении. Сохраняются:

- таблицы `accounts_*`, первичные ключи, внешние связи и ограничения;
- `ContentType`, права пользователей и адреса моделей в Django Admin;
- `AUTH_USER_MODEL = "accounts.User"` и история `accounts/migrations`;
- все 56 адресов и имён API.

Разделение кода не требует переименовывать таблицы, копировать документы или
применять новую миграцию. Исторические миграции остаются в `accounts/migrations`;
их нельзя удалять или переносить в новые приложения. Изменения полей существующих
моделей по-прежнему создают миграции для `accounts`.

`accounts.models`, `accounts.serializers`, `accounts.views`,
`accounts.dashboard_views` и `accounts.docx_preview` сохраняют старые импорты.
Новый код должен импортировать сущности из приложения-владельца, например
`from submissions.models import ThematicAccountSubmission`.
`accounts.dashboard_urls` собирает маршруты приложений, сохраняя `/api/dashboard/`.
Адреса чата остаются под `/api/auth/chat/`.

## Проверки

Запускать из каталога `backend`, чтобы Django обнаружил все тесты:

```sh
cd backend
venv/bin/python manage.py check
venv/bin/python manage.py makemigrations --check --dry-run
venv/bin/python manage.py test --noinput
```

`common.tests` сравнивает адреса API и идентификаторы моделей с состоянием до
разделения, проверяет регистрацию админки и отсутствие расхождений с миграциями.
`submissions.tests.test_document_workflow` проверяет полный путь документа с
настоящим JWT-входом: отправка → получение своей частью → пересылка → получение
администратором → запрос исправления → согласование → сохранение исправления.
Отдельно проверяется откат отправки и пересылки журнала при ошибке записи истории.

Тесты используют отдельную тестовую базу. Для PostgreSQL учётной записи тестового
сервера нужно право создания тестовых баз. Не указывать рабочую базу в
`DATABASES["default"]["TEST"]["NAME"]`.

## Исправления, обнаруженные при проверке

- Удаление недели расписания ограничено администратором, владельцем либо
  допустимой старой пользовательской неделей без владельца. Застава больше не
  может удалить чужую или системную неделю.
- Пересылка журнала вместе с историей выполняется в одной транзакции.
  Ошибка записи истории не оставляет частично пересланный документ.
- Список отправленных документов загружает статус запроса на исправление через
  `select_related`, без отдельного запроса для каждого документа.
- Тест рейтинга учитывает существующее поведение: справочные заставы своей части
  отображаются и с нулём документов; чужие части не попадают в рейтинг.

## Работа под нагрузкой и обновление сервера

Разделение приложений упрощает сопровождение, но само по себе не увеличивает
пропускную способность. Для оценки 400 пользователей в день нужны пиковая
одновременная нагрузка, объём документов, время ответов и параметры сервера.
Django рекомендует сначала измерять запросы и время выполнения:
[оптимизация запросов к базе](https://docs.djangoproject.com/en/4.2/topics/db/optimization/).

Перед обновлением сервера проверить изменения на копии окружения и базы,
сохранить резервную копию базы и медиафайлов, развернуть весь каталог `backend`,
проверить `migrate --plan`, применить ожидаемые миграции и перезапустить Gunicorn.
После перезапуска проверить вход и путь тестового документа между ролями.
Рефакторинг не меняет конфигурацию Nginx, Gunicorn или выбор базы данных.

В репозитории пример Nginx использует `/opt/munara/current/backend/staticfiles/`
и `/opt/munara/current/backend/media/`, тогда как настройки Django задают
`/home/sysadmin/static` и `/home/sysadmin/media`. Перед развёртыванием сверить
эти пути с действующей конфигурацией сервера: локальные API-тесты не проверяют
отдачу файлов через рабочий Nginx.
